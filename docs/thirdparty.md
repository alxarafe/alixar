# ThirdParty

## 1. Purpose and decision status

This document defines the canonical Alixar ThirdParty contract for the basic
lifecycle characterized in `THIRDPARTY-REF-001`.

```text
THIRDPARTY-REF-001
    ↓
legacy evidence

THIRDPARTY-001
    ↓
explicit canonical Alixar decisions

future implementation
    ↓
Alixar domain + persistence + API + security + audit

future Solucar slice
    ↓
web UX
```

Dolibarr is evidence. It is not the future contract. Legacy names such as
`llx_*`, `socid`, `fk_soc`, `nom`, `fournisseur`, `idprof1` and the numeric
`client` codes are confined to the legacy boundary and to the evidence, decision
and migration sections of this document. They do not form part of the canonical
Alixar API unless a decision below explicitly says so.

At this snapshot the basic ThirdParty lifecycle is **DECIDED** and partially
implemented. `THIRDPARTY-002A` provides native Alixar persistence plus the
canonical create and read operations, their permissions and the create audit
event. `THIRDPARTY-002B` provides the canonical list with pagination and exact
boolean filters. `THIRDPARTY-002C` provides the canonical partial update with
presence-aware merge-patch semantics, no-op detection and the update audit event.
Delete remains a future slice (`THIRDPARTY-002D`). Native Contact create/read
persistence and the optional restrictive Contact → ThirdParty relationship are
implemented by `CONTACT-002`.

## 2. Scope

In scope for this decision:

- identity;
- name;
- customer/prospect classification;
- supplier condition;
- active/inactive state;
- basic ES fiscal identity;
- flat basic address and contact data;
- create, read, list, partial update and delete semantics;
- the minimal Contact → ThirdParty relationship;
- canonical errors;
- future authorization;
- future audit;
- future data-migration invariants.

Out of scope and still pending:

- commercial alias;
- advanced fiscal and tax rules;
- structured addresses, states, provinces and geography;
- bank accounts, accounts and representatives;
- categories and supplier categories;
- discounts, payment terms and price levels;
- notifications, documents and merge;
- outstanding invoices, orders and proposals;
- accounting;
- extrafields;
- historical import;
- Solucar UI implementation.

## 3. Decision vocabulary

Each relevant legacy behaviour is classified as:

| Decision | Meaning |
|----------|---------|
| `KEEP` | Alixar preserves the relevant legacy behaviour. |
| `ADAPT` | Alixar preserves the business intent through a canonical model or contract. |
| `REPLACE` | Alixar provides a clearer capability that supersedes the legacy behaviour. |
| `DISCARD` | Alixar consciously does not reproduce the legacy behaviour. |

"Dolibarr does this" is not, by itself, a justification. Each decision also
considers business intent, contract clarity, consistency with Alixar, security,
data integrity, evolvability, Contact compatibility, future data migration and
KISS/YAGNI.

## 4. Canonical resource and identity

### 4.1 Resource name

| Concept | Canonical value |
|---------|-----------------|
| Domain concept | `ThirdParty` |
| Collection name | `thirdparties` |
| Canonical API base path | `/api/thirdparties` |
| Future authorization namespace | `thirdparties.*` |
| Future audit resource type | `THIRD_PARTY` |

### 4.2 Identity

The canonical ThirdParty identifier is:

```text
id: 64-bit signed integer (JSON number)
```

It is:

- generated by Alixar;
- positive;
- immutable;
- never reused within a deployment;
- independent from the legacy Dolibarr `rowid`;
- serialized as a JSON number, never as a string.

This choice preserves compatibility with the existing Contact contract, whose
`thirdPartyId` is a nullable `Long` and whose own `id` is a `long`
(`Contact.java`, `CreateContactRequest.thirdPartyId`). Authentication users use
UUIDs because they are security identities, not ERP business entities.

The legacy Dolibarr identifier does **not** form part of the canonical domain.
No `legacyId`, `dolibarrId`, `socid` or `fk_soc` field is added to the canonical
resource.

Future data migration will conceptually maintain an explicit mapping between a
legacy record key and the Alixar-generated canonical identifier. The mapping
belongs to the migration process, not to the canonical ThirdParty contract. No
assumption may be made that a legacy `rowid` equals an Alixar `id`, and Contacts
must be migrated through the same mapping.

## 5. Canonical fields

The first canonical representation is deliberately flat. It does not introduce
an Address value object or an embedded fiscal framework.

| Field | Type | Required | Default | Notes |
|-------|------|----------|---------|-------|
| `id` | integer (64-bit) | read-only | generated | Canonical Alixar identity |
| `name` | string | yes | none | Trimmed, non-blank; duplicates allowed |
| `customer` | boolean | no | `false` | Customer classification |
| `prospect` | boolean | no | `false` | Prospect classification |
| `supplier` | boolean | no | `false` | Supplier condition, independent of classification |
| `active` | boolean | no | `true` | Effective active/inactive state |
| `taxIdentifier` | string or null | no | `null` | ES CIF/NIF; no format validation in the first slice |
| `intraCommunityVatNumber` | string or null | no | `null` | Intra-community VAT; no format or VIES validation |
| `address` | string or null | no | `null` | Flat free-form address line |
| `postalCode` | string or null | no | `null` | Postal code |
| `town` | string or null | no | `null` | Town or city |
| `countryCode` | string or null | no | `null` | Uppercase ISO 3166-1 alpha-2 code; catalogue validation pending |
| `email` | string or null | no | `null` | Not unique; no strict format validation in the first slice |
| `phone` | string or null | no | `null` | Free-form; no format validation |
| `website` | string or null | no | `null` | Free-form; no URL format validation |

Initial storage limits, aligned with the observed legacy columns:

| Field | Maximum length |
|-------|----------------|
| `name` | 128 |
| `taxIdentifier` | 128 |
| `intraCommunityVatNumber` | 20 |
| `address` | 255 |
| `postalCode` | 25 |
| `town` | 50 |
| `countryCode` | 2 |
| `email` | 128 |
| `phone` | 30 |
| `website` | 255 |

These limits are implementation constraints for `THIRDPARTY-002A`, not an
invitation to copy the rest of the legacy schema. A future task may revisit them
with an explicit decision.

Optional text fields are canonicalized as follows:

- leading and trailing whitespace is trimmed;
- an empty or whitespace-only value becomes `null`;
- no optional text field is returned as an empty string.

Read responses include every field. Absent optional values are represented as
JSON `null`, never as an empty string.

## 6. Name

Decision:

- `name` is mandatory;
- `null` is rejected;
- the value is trimmed;
- a value that is empty or whitespace-only after trimming is rejected;
- internal whitespace is preserved;
- duplicate names are allowed;
- name updates are allowed;
- an update that would produce a blank name is rejected, not silently ignored.

The canonical error is `VALIDATION_REQUIRED` with `field: "name"` and HTTP
`400`. The legacy HTTP `500` for a blank name is not reproduced.

Duplicate names are a real business possibility. No uniqueness constraint is
introduced, and future merging or deduplication is a separate capability
(`TP-MERGE`).

## 7. Alias / alternative name

The legacy `name_alias` field is observed but is not part of the first canonical
contract. No current use case requires it, and adding it only because Dolibarr
has it would violate YAGNI.

Decision:

```text
TP-ALIAS = PENDING
```

The capability remains registered in the migration master. A future task may add
a semantic alias or trade name with its own contract decision. It is not silently
dropped.

## 8. Customer/prospect classification

The legacy numeric `client` codes are not exposed:

```text
0 → neither
1 → customer
2 → prospect
3 → customer + prospect
```

Canonical representation:

```text
customer: boolean
prospect: boolean
```

This pair represents exactly the four observed business combinations without
depending on `0/1/2/3`:

| Business meaning | `customer` | `prospect` |
|------------------|------------|------------|
| Neither | `false` | `false` |
| Customer | `true` | `false` |
| Prospect | `false` | `true` |
| Customer and prospect | `true` | `true` |

Rules:

- both default to `false`;
- all four combinations are valid;
- transitions between any two combinations are allowed;
- the two flags are independent;
- there is no persisted derived `prospect` status;
- JSON serialization uses booleans, never numeric codes or strings.

List filters:

- `customer=true|false` matches the customer flag exactly;
- `prospect=true|false` matches the prospect flag exactly;
- filters combine with each other and with `supplier` and `active` using `AND`.

---

## 9. Supplier

The legacy `fournisseur` name and numeric flag are not exposed.

Canonical property:

```text
supplier: boolean
```

Rules:

- default `false`;
- independent of `customer` and `prospect`;
- may coexist with any customer/prospect combination;
- may be changed independently at create and update time;
- expresses that a ThirdParty can act as a supplier, not that a complete
  procurement module exists;
- list filter `supplier=true|false` matches the flag exactly.

Procurement, supplier categories, supplier pricing and supplier documents remain
out of scope.

---

## 10. Active/inactive state

The effective legacy field is `status` (`1` active, `0` inactive). The legacy
`statut` property is not the effective state and is not exposed.

Canonical property:

```text
active: boolean
```

Rules:

- default `true`;
- `true` means active, `false` means inactive;
- both states are readable and listable;
- inactive records are not deleted and do not disappear from reads;
- list filter `active=true|false` matches the flag exactly;
- this first contract does not decide downstream commercial effects of
  inactivity; those belong to later domain slices.

## 11. Fiscal identity (ES basic)

Field support and format validation are distinct decisions.

### 11.1 Included in the first contract

| Canonical field | Legacy evidence | Semantic meaning |
|-----------------|-----------------|------------------|
| `taxIdentifier` | `idprof1` | Spanish CIF/NIF |
| `intraCommunityVatNumber` | `tva_intra` | Intra-community VAT identifier |

Both are optional, trimmed, nullable and non-unique.

### 11.2 Validation

The first contract supports the fields but does **not** validate:

- CIF/NIF format or check digit;
- intra-community VAT format;
- VIES existence;
- uniqueness;
- fiscal obligations derived from country or activity.

The reference evidence observed that legacy accepts invalid-looking fiscal values
and duplicates. Alixar does not turn that observation into a permanent promise,
but it also does not introduce unstudied Spanish validation in this slice. Format
validation remains pending.

### 11.3 Deferred

The following legacy fiscal data is not part of the first canonical contract and
must remain registered as pending:

- `idprof2` (ES social security identifier);
- `idprof3` (CNAE);
- `idprof4`, `idprof5`, `idprof6`;
- `tva_assuj`, `vat_reverse_charge`, `localtax1_assuj`, `localtax2_assuj`;
- EUID and any advanced tax framework.

Future data migration must not silently discard these values. The importer must
either preserve them in a migration-owned structure or report them explicitly as
unsupported.

## 12. Basic address and contact data

The first contract uses flat optional fields, not an Address aggregate:

- `address`;
- `postalCode`;
- `town`;
- `countryCode`;
- `email`;
- `phone`;
- `website`.

Decisions:

- every field is optional and nullable;
- blank input becomes `null`;
- `email` is not unique;
- `email` format is not strictly validated in the first slice, prioritizing
  migration compatibility over a new unapproved rule;
- `phone` and `website` are free-form in the first slice;
- `countryCode` is stored uppercase as an ISO 3166-1 alpha-2 code, but validation
  against a canonical country catalogue is pending;
- no state/province, mobile phone, fax, social network or structured address is
  included.

Basic flat address and contact fields are part of `TP-BASIC`. Structured
addresses and geography remain `TP-ADDRESS`, still pending.

## 13. Create

### 13.1 Endpoint

```text
POST /api/thirdparties
Content-Type: application/json
```

### 13.2 Request

Required:

- `name`.

Optional:

- `customer`;
- `prospect`;
- `supplier`;
- `active`;
- `taxIdentifier`;
- `intraCommunityVatNumber`;
- `address`;
- `postalCode`;
- `town`;
- `countryCode`;
- `email`;
- `phone`;
- `website`.

Defaults:

```text
customer = false
prospect = false
supplier = false
active   = true
optional text fields = null
```

Minimal example:

```json
{
  "name": "Acme Ibérica, S.L."
}
```

### 13.3 Response

```text
201 Created
Location: /api/thirdparties/{id}
```

```json
{
  "id": 42
}
```

The response is not HTTP `200` with a bare integer. The created identifier is a
JSON object member with a numeric value, and the `Location` header identifies the
new canonical resource.

### 13.4 Errors

- missing, `null` or blank `name` → `400 VALIDATION_REQUIRED` with `field: "name"`;
- unknown JSON member or invalid value type → `400 VALIDATION_INVALID`;
- unauthenticated → `401`;
- authenticated without `thirdparties.manage` → `403`;
- unsupported media type → `415`;
- audit append failure under `BASIC`/`SELECTIVE` → `503 AUDIT_UNAVAILABLE` and
  no partial creation.

The future endpoint follows the existing authentication and CSRF rules. Session
authentication uses CSRF protection; Bearer authentication does not.

## 14. Read

### 14.1 Endpoint

```text
GET /api/thirdparties/{id}
```

Response `200` with the full canonical representation, including `null` for
absent optional fields.

Example:

```json
{
  "id": 42,
  "name": "Acme Ibérica, S.L.",
  "customer": true,
  "prospect": false,
  "supplier": false,
  "active": true,
  "taxIdentifier": "B12345678",
  "intraCommunityVatNumber": "ESB12345678",
  "address": "Calle Mayor 1",
  "postalCode": "28001",
  "town": "Madrid",
  "countryCode": "ES",
  "email": "info@example.test",
  "phone": "+34 910 000 000",
  "website": "https://example.test"
}
```

### 14.2 Not found and invalid identifiers

- a positive numeric identifier that does not exist → `404 THIRD_PARTY_NOT_FOUND`;
- a non-numeric, zero or negative identifier → `400 VALIDATION_INVALID` with
  `field: "id"`;
- no request may return a specimen object.

Legacy `GET /thirdparties/0` returning a generated specimen is **DISCARDED**.
Zero is not a valid canonical identity, and Alixar has no independent need for a
specimen object.

## 15. List

### 15.1 Endpoint

```text
GET /api/thirdparties
```

### 15.2 Pagination

- `page` is 0-based and defaults to `0`;
- `size` is between `1` and `100` and defaults to `20`;
- invalid `page` or `size` → `400 VALIDATION_INVALID` with the offending field.

These defaults follow the existing administrative user list convention, so the
project does not introduce a second pagination shape.

Response:

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "total": 0
}
```

### 15.3 Empty result

An empty result is `200` with `items: []` and `total: 0`. It is never `404`.
The legacy `404` for an empty list is **REPLACED** by the canonical collection
semantics.

### 15.4 Ordering

The first contract has one deterministic order:

```text
id ASC
```

Client-selected sorting, `sqlfilters`, database column names, arbitrary property
selection and pagination envelopes copied from Dolibarr are not exposed.

### 15.5 Filters

Optional exact-match boolean filters:

- `customer`;
- `prospect`;
- `supplier`;
- `active`.

Filters combine with `AND`. Unknown query parameters are not, by themselves, a
canonical error condition. Query binding uses standard Spring behaviour unless
this small closed filter set is validated explicitly where that is natural and
simple. Global rejection of unknown query parameters is not required and must
not require dedicated infrastructure. Client-selected sorting is not part of the
contract.

### 15.6 Text search

Free-text search by name, email, tax identifier or address is not part of the
first contract. It is not justified by the first slice. It remains a future
capability if a real use case requires it.

### 15.7 Errors

- unauthenticated → `401`;
- authenticated without `thirdparties.read` → `403`;
- invalid pagination or invalid value for a known filter → `400 VALIDATION_INVALID`;
- audit append failure if read auditing is ever enabled for this resource →
  `503 AUDIT_UNAVAILABLE` without data (not applicable to the current baseline).

### 15.8 Implementation status

`THIRDPARTY-002B` implements `GET /api/thirdparties` with 0-based pagination,
size `1..100`, deterministic `id ASC` ordering, the exact boolean filters and
`thirdparties.read` authorization. Listing does not append ThirdParty audit
events.

## 16. Partial update

### 16.1 HTTP semantics

The preferred media type is:

```text
PATCH /api/thirdparties/{id}
Content-Type: application/merge-patch+json
```

The functional decision is an explicit partial update, not a partial `PUT`.
Using `PUT` for partial updates only because Dolibarr does so is rejected. When
`application/merge-patch+json` is used, the semantics are JSON Merge Patch
(RFC 7396).

Implementation restriction: `application/merge-patch+json` is the preferred
contract only if the update slice (`THIRDPARTY-002C`) can implement it cleanly
with Spring and the current design, for example with a dedicated request DTO that tracks field
presence and standard Spring MVC. It must not introduce generic merge-patch
infrastructure, a framework extension, or a complex abstraction solely to
support RFC 7396. If that clean implementation is not possible,
`THIRDPARTY-002C` must use `application/json` with the same functional rules in
section 16.2 rather than add that infrastructure. Those functional rules are
binding regardless of the selected media type.

### 16.2 Rules

- omitted members remain unchanged;
- `null` clears an optional field;
- `null` for a non-nullable member (`name`, `customer`, `prospect`, `supplier`,
  `active`) is rejected;
- a blank or whitespace-only `name` is rejected with `VALIDATION_REQUIRED`, not
  silently ignored;
- `id` is immutable and cannot be patched;
- unknown JSON members are rejected;
- `customer` and `prospect` may change independently to any of the four valid
  combinations;
- `supplier` may change independently;
- `active` may change independently;
- fiscal and basic contact/address fields may be set, changed or cleared.

Example:

```json
{
  "name": "Acme Ibérica Distribución, S.L.",
  "active": false,
  "email": null
}
```

### 16.3 Response and errors

- success → `200` with the full updated canonical representation;
- non-existent identifier → `404 THIRD_PARTY_NOT_FOUND`;
- invalid identifier → `400 VALIDATION_INVALID`;
- missing/blank name or invalid member → `400`;
- unauthenticated → `401`;
- authenticated without `thirdparties.manage` → `403`;
- audit failure under `BASIC`/`SELECTIVE` → `503 AUDIT_UNAVAILABLE` and the
  update is not committed;
- a PATCH that produces no actual change records no audit event.

### 16.4 Implementation status

`THIRDPARTY-002C` implements `PATCH /api/thirdparties/{id}` with
`application/merge-patch+json`, explicit member-presence tracking and
`application/json` requests rejected as unsupported media types. It rejects
unknown members and body `id`, applies the shared normalization rules, protects
the operation with `thirdparties.manage`, requires CSRF for session PATCH, and
returns the full canonical representation. A no-op performs no `UPDATE` and
records no audit event. A real change appends `THIRD_PARTY_UPDATED` atomically;
an append failure returns `503 AUDIT_UNAVAILABLE` and rolls back the update.

Delete and the canonical linked-Contact conflict remain outside this slice.
Native Contact persistence and the restrictive relationship are implemented by
`CONTACT-002`.

## 17. Delete

### 17.1 Semantics

The first contract uses physical deletion:

```text
DELETE /api/thirdparties/{id}
```

- success → `204 No Content` with no body;
- non-existent positive identifier → `404 THIRD_PARTY_NOT_FOUND`;
- invalid identifier → `400 VALIDATION_INVALID`;
- unauthenticated → `401`;
- authenticated without `thirdparties.manage` → `403`.

No soft-delete or deleted marker is introduced by speculation.

### 17.2 Linked Contacts

If the ThirdParty has one or more linked Contacts, deletion is rejected:

```text
409 THIRD_PARTY_DELETE_CONFLICT
```

The client must first unlink or reassign the Contacts through the Contact
lifecycle. Alixar does **not** reproduce the legacy application-level cascade
that deletes linked Contacts.

This is the simplest and safest behaviour compatible with the current business
evidence:

- it avoids accidental loss of Contact data;
- it keeps deletion explicit;
- it prepares a future restrictive database foreign key;
- it does not require a cascading operation that is not yet justified.

Deleting a Contact never deletes its ThirdParty.

### 17.3 Other blocking children

Future modules (orders, invoices, proposals, projects, etc.) may add their own
restrictive deletion rules and conflict errors. They are outside this contract
and are not simulated now.

## 18. Contact → ThirdParty relationship

The existing Contact contract uses `thirdPartyId`, a nullable `Long`. It is
preserved.

Decisions:

- a Contact may exist without a ThirdParty (`thirdPartyId = null`);
- when present, `thirdPartyId` must reference an existing canonical ThirdParty;
- the relationship is optional many-to-one: many Contacts may reference one
  ThirdParty, and one Contact references at most one ThirdParty;
- changing the association is allowed through the future Contact update
  lifecycle: setting a valid identifier links the Contact, and setting `null`
  makes it standalone;
- supplying a non-existent ThirdParty on Contact create/update keeps the existing
  canonical error `CONTACT_INVALID_THIRD_PARTY_REFERENCE` (HTTP `422`);
- deleting a ThirdParty with linked Contacts is rejected with
  `THIRD_PARTY_DELETE_CONFLICT` until the Contacts are unlinked or reassigned;
- deleting a Contact does not affect the ThirdParty.

The native `contact` table implements a real nullable foreign key
`contact.third_party_id → third_party(id)` with `ON DELETE RESTRICT`; it never
cascades. Contact creation pre-validates the reference and returns
`422 CONTACT_INVALID_THIRD_PARTY_REFERENCE` when the ThirdParty does not exist.
The canonical `409 THIRD_PARTY_DELETE_CONFLICT` response remains part of the
pending `THIRDPARTY-002D` delete slice.

The canonical Contact representation does not yet embed a ThirdParty object or
denormalized ThirdParty name. `thirdPartyId` remains the canonical reference.

## 19. Unknown fields and parameters

Legacy Dolibarr ignores unknown fields. Alixar deliberately does **not** copy
that behaviour for JSON request bodies.

Decision:

- unknown JSON members in create and partial update requests are rejected with
  `400 VALIDATION_INVALID` and the offending `field`;
- unknown query parameters are not, by themselves, a canonical error condition;
- query binding follows standard Spring behaviour unless an operation has a
  small closed parameter set whose explicit validation is natural and simple;
- global rejection of unknown query parameters is not required and must not
  require dedicated infrastructure;
- unsupported sorting is not part of the contract, so clients must not rely on
  it.

This favours clear JSON contracts and early detection of client body errors
without turning query-parameter strictness into a new framework concern. It is a
deliberate compatibility break for JSON bodies, not an assumption that
compatibility requires leniency.

## 20. Canonical errors

Errors use the existing RFC 9457 `ProblemDetail` pattern with stable `type`,
`code` and, where applicable, `field` values. Human-readable `title` and `detail`
come from module-owned i18n bundles when implemented.

| HTTP | Code | When | Notes |
|------|------|------|-------|
| `400` | `VALIDATION_REQUIRED` | Missing, `null` or blank required `name` | `field: "name"` |
| `400` | `VALIDATION_INVALID` | Unknown JSON member, invalid type, invalid identifier, invalid pagination or invalid value for a known filter | `field` identifies the offending member or parameter |
| `401` | Existing authentication result | Missing or invalid authentication | Existing security contract |
| `403` | Existing authorization result | Authenticated without the required permission | Existing security contract |
| `404` | `THIRD_PARTY_NOT_FOUND` | Positive identifier not found | Also used by update and delete |
| `409` | `THIRD_PARTY_DELETE_CONFLICT` | Delete blocked by linked Contacts | No cascade |
| `415` | Framework result | Unsupported media type | No legacy SQL detail |
| `503` | `AUDIT_UNAVAILABLE` | Required audit event cannot be appended | Existing fail-closed convention |

Stable `type` identifiers follow the existing URN convention:

```text
urn:alixar:error:validation-required
urn:alixar:error:validation-invalid
urn:alixar:error:third-party-not-found
urn:alixar:error:third-party-delete-conflict
urn:alixar:error:audit-unavailable
```

Additional decisions:

- `CONTACT_INVALID_THIRD_PARTY_REFERENCE` remains the Contact-side error for an
  invalid `thirdPartyId`;
- validation failures never return HTTP `500`;
- errors never expose SQL constraint names, table names, column names or legacy
  field names;
- no duplicate-name error exists, because duplicates are allowed;
- no email-uniqueness error exists, because email is not unique;
- advanced fiscal validation errors are not introduced in the first contract.

These codes are part of this contract. `THIRDPARTY-002A` implements the create
and read codes; `THIRDPARTY-002C` implements the update codes; the delete slice
implements the remaining delete code.

## 21. Authorization

ThirdParty follows the existing RBAC model: authorization by permission code,
never by role name.

Minimal permissions:

| Permission | Meaning | Protects |
|------------|---------|----------|
| `thirdparties.read` | Read ThirdParty data | `GET /api/thirdparties`, `GET /api/thirdparties/{id}` |
| `thirdparties.manage` | Create, update and delete ThirdParty data | `POST`, `PATCH`, `DELETE` |

Rationale:

- two permissions are enough for the current use cases;
- no field-level permissions, ACL per object, role hierarchy, ABAC or hardcoded
  role names are introduced;
- a separate delete permission is not justified by a current real need.

`THIRDPARTY-002A` seeds both permissions and assigns them to the built-in
`system-admin` role. `GET` operations require `thirdparties.read`; create and
partial update require `thirdparties.manage`. They are enforced identically for
session and Bearer authentication.

Existing HTTP semantics remain:

| Caller | Result |
|--------|--------|
| Not authenticated | `401 Unauthorized` |
| Authenticated without the required permission | `403 Forbidden` |
| Authenticated with the required permission | Request reaches the operation |

These rules apply identically to session and Bearer authentication.

## 22. Audit

### 22.1 Baseline requirement

ThirdParty mutations are part of the future `BASIC` audit baseline:

| Operation | Action | Resource type | Result |
|-----------|-----------------|---------------|--------|
| Create | `THIRD_PARTY_CREATED` | `THIRD_PARTY` | `SUCCESS` |
| Partial update with real change | `THIRD_PARTY_UPDATED` | `THIRD_PARTY` | `SUCCESS` |
| Successful delete | `THIRD_PARTY_DELETED` | `THIRD_PARTY` | `SUCCESS` |

Rules:

- under `OFF`, no ThirdParty event is appended;
- under `BASIC` and `SELECTIVE`, the event is mandatory and fail-closed;
- the event is appended in the same transaction as the business change;
- if the append fails, the mutation rolls back and returns
  `503 AUDIT_UNAVAILABLE`;
- a no-op update records no event;
- rejected validation, not-found or delete-conflict operations record no
  ThirdParty mutation event;
- authorization denials continue to use the existing `ACCESS_DENIED`
  `HTTP_REQUEST` mechanism;
- the event records the canonical resource identifier and action, not the full
  ThirdParty object, fiscal identifiers or other business payload.

### 22.2 Reads

ThirdParty reads are **not** audited in the baseline.

`SELECTIVE` read auditing for `THIRD_PARTY` is a future extension. The current
read policy only supports `USER` and `ROLE`; ThirdParty read auditing must not be
claimed as available until it is explicitly implemented. If added later, it
should follow the existing `READ_QUERY` / `READ_OBJECT` rules.

### 22.3 Implementation status

```text
Canonical requirement: decided in this document.
Implemented in THIRDPARTY-002A:
  THIRD_PARTY_CREATED, resource type THIRD_PARTY, result SUCCESS
  appended atomically with the create transaction
Implemented in THIRDPARTY-002C:
  THIRD_PARTY_UPDATED, resource type THIRD_PARTY, result SUCCESS
  appended atomically with real updates; no-op updates record no event
Not implemented yet:
  THIRD_PARTY_DELETED (future delete slice)
  ThirdParty read auditing (not part of the baseline)
```

The ThirdParty mutation events record only the canonical identifier, action,
resource type and result. They never record the full object, fiscal
identifiers, address, email or other business payload. Under `OFF` no
ThirdParty event is appended; under `BASIC` and `SELECTIVE` create and real
update events are mandatory and fail-closed, so an audit append failure rolls
back the business change and returns `503 AUDIT_UNAVAILABLE`.

The migration master tracks the aggregate and its sub-capabilities separately
and keeps `TP-BASIC` as `IN_PROGRESS`.

## 24. Data-migration invariants

Data migration remains:

```text
PENDING
```

No importer is designed in this task. The following invariants must be respected
when it is designed:

- duplicate names are valid and must not be merged automatically;
- email is not a unique identifier;
- `client` values map losslessly to `(customer, prospect)`:
  `0=(false,false)`, `1=(true,false)`, `2=(false,true)`, `3=(true,true)`;
- `fournisseur` maps to the independent `supplier` flag;
- `status` maps to `active` (`1=true`, `0=false`);
- a Contact without a ThirdParty remains valid (`thirdPartyId = null`);
- linked Contacts must be migrated through the explicit legacy-to-canonical
  ThirdParty mapping; a legacy `fk_soc` is never assumed to equal a canonical
  `id`;
- legacy `name_alias`, `idprof2`, `idprof3`, `idprof4`, `idprof5`, `idprof6`,
  tax-subjection flags and other non-characterized fiscal data must not be
  silently discarded;
- legacy rows with missing or blank names must be reported or quarantined, not
  silently renamed or dropped;
- empty strings and nulls must be normalized to canonical `null` for absent
  optional values without losing meaningful non-empty values;
- numeric `country_id` values must be mapped to canonical country codes through
  an explicit catalogue mapping;
- the legacy application-level Contact cascade must not be interpreted as
  evidence that Alixar should delete Contacts automatically.

## 25. Legacy quirks decision table

| Legacy behavior | Evidence | Canonical decision | Rationale |
|-----------------|----------|--------------------|-----------|
| Create returns HTTP `200` and a bare integer ID | `THIRDPARTY-REF-001` create matrix | `REPLACE`: `201` + `Location` + `{"id": ...}` | Clear REST semantics and a stable body |
| `GET /thirdparties/0` returns a specimen object | `THIRDPARTY-REF-001` read | `DISCARD`: `0` is an invalid identifier | No canonical need for specimen data; avoids an accidental contract |
| Empty list returns HTTP `404` | `THIRDPARTY-REF-001` list | `REPLACE`: `200` with empty `items` | An empty collection is not a missing resource |
| Blank create name returns HTTP `500` | `THIRDPARTY-REF-001` create matrix | `REPLACE`: `400 VALIDATION_REQUIRED` | Validation is a client error, not a server failure |
| Unknown create JSON body fields are ignored | `THIRDPARTY-REF-001` create matrix | `REPLACE`: reject with `400 VALIDATION_INVALID` | Detect client mistakes and keep a strict JSON contract |
| Numeric `client` codes `0/1/2/3` | `THIRDPARTY-REF-001` classification | `ADAPT`: independent `customer` and `prospect` booleans | Preserves all four business combinations without legacy codes |
| `fournisseur` naming and numeric flag | `THIRDPARTY-REF-001` supplier | `ADAPT`: independent `supplier` boolean | Semantic canonical name and type |
| `status` / `statut` ambiguity | `THIRDPARTY-REF-001` status | `ADAPT`: single `active` boolean | One explicit effective state; legacy `statut` is discarded |
| `PUT` behaves as a partial update | `THIRDPARTY-REF-001` update | `ADAPT`: `PATCH` with partial-update semantics; `application/merge-patch+json` is preferred subject to section 16.1 | Explicit HTTP partial-update semantics |
| Deleting a ThirdParty cascades to linked Contacts | `THIRDPARTY-REF-001` delete | `DISCARD`: reject with `409` until Contacts are unlinked or reassigned | Prevents accidental data loss and matches a restrictive relation |
| Mixed `null` and empty-string representation | `THIRDPARTY-REF-001` read | `ADAPT`: absent optional values are always `null` | One deterministic representation |
| Numeric values serialized as strings | `THIRDPARTY-REF-001` read | `REPLACE`: JSON numbers and booleans | Stable, typed contract |
| Duplicate names are allowed | `THIRDPARTY-REF-001` duplicates | `KEEP`: duplicates allowed | Name is not an identity |
| Name is trimmed before persistence | `THIRDPARTY-REF-001` create | `KEEP`: trim and reject blank | Normalized input without changing business meaning |
| Email is optional, non-unique and not format-validated | `THIRDPARTY-REF-001` email | `KEEP`: optional and non-unique; format validation pending | Migration compatibility; no approved strict rule |
| Fiscal identifiers are accepted without format/uniqueness validation | `THIRDPARTY-REF-001` fiscal | `ADAPT`: support fields without validation in the first slice | Field support now, validation later with an explicit decision |
| `ref` mirrors `name` | `THIRDPARTY-REF-001` read | `DISCARD`: no separate canonical `ref` | One canonical business name |
| `country_id` is numeric and `country_code` is derived | `THIRDPARTY-REF-001` read | `ADAPT`: canonical `countryCode`; catalogue mapping pending | Semantic public representation |
| `name_alias` exists | `THIRDPARTY-REF-001` fields | `PENDING`: not in the first contract | No current use case; kept in the master |
| List uses `limit`/`page` and DB sorting | `THIRDPARTY-REF-001` list | `ADAPT`: 0-based `page`/`size`, fixed `id ASC` order | Stable pagination without exposing DB columns |
| Delete returns an HTTP `200` success object | `THIRDPARTY-REF-001` delete | `REPLACE`: `204 No Content` | Standard deletion result with no redundant body |
| Physical deletion removes the row | `THIRDPARTY-REF-001` delete | `KEEP`: physical deletion | No soft-delete requirement exists yet |
| Contact `socid` / `fk_soc` naming | `THIRDPARTY-REF-001`; `CONTACT-REF-001` | `ADAPT`: canonical `thirdPartyId` | Existing Contact contract already uses the canonical name |
| Blocking child objects return `409` | `THIRDPARTY-REF-001` delete (source-derived) | `ADAPT`: future modules add restrictive conflicts | Integrity is preserved; specific modules are out of scope |
